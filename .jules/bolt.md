
## 2024-05-24 - N+1 Anti-Pattern in `ListRuns`
**Learning:** The method `ListRuns` in `apps/api/internal/store/postgres.go` originally gathered run IDs using a query and then ran an N+1 set of subqueries inside a loop using `GetRun` for each ID to rebuild standard data mapping, causing an unnecessary load when a `LEFT JOIN` over reports and scenario versions mapped directly into standard types mitigates this immediately.
**Action:** Always inspect the `List` methods inside raw SQL files to ensure they don't depend on iteration-based calls to `Get` methods. Use efficient `LEFT JOIN` queries instead.
## 2025-02-18 - Prometheus metrics endpoint loading full objects instead of aggregating in DB
**Learning:** The `/metrics` endpoint in the `apps/api/internal/httpapi/server.go` was calling `store.ListRuns()` which executed `SELECT ... FROM runs LEFT JOIN reports ...` to pull the complete history of runs, including large JSON snapshots and reports, just to count statuses. In an application with thousands of runs, pulling all historical objects into memory on every metrics scrape (typically every 15s) is a massive O(N) memory and CPU bottleneck.
**Action:** When adding or optimizing metrics endpoints that need counts, always push the aggregation to the database (`SELECT status, count(*) FROM ... GROUP BY status`) using a targeted store method like `CountRunsByStatus() (map[RunStatus]int, int)` instead of iterating over a full `List()` response in memory.
